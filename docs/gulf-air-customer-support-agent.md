# Gulf Air Customer Support Copilot

## Document purpose

This document describes the Gulf Air customer-support experience implemented by the LangChain.js API. It is intended for product owners, solution architects, developers, testers, and operations teams who need a reliable description of the agent's capabilities, interfaces, data dependencies, limitations, and prompt usage.

## 1. Executive summary

The Gulf Air Customer Support Copilot is a conversational support experience for common passenger questions and disruption scenarios. It is designed to provide concise, policy-grounded guidance; use the active passenger context when supplied; ask focused follow-up questions; respond in English or Arabic; and direct sensitive matters to official human support.

The current implementation is a **demonstration/reference implementation**, not a production airline servicing system. The chat response is generated by the configured language model using local policy and sample data. It does not perform live booking, ticketing, payment, check-in, baggage tracking, refund processing, or agent transfer.

## 2. Scope and capability matrix

| Capability | Intended user outcome | Current implementation boundary |
|---|---|---|
| Flight disruption guidance | Understand delay, cancellation, diversion, and recovery guidance | Uses local sample disruption data and policy files; not a live flight-status feed |
| Rebooking and recovery information | Review possible recovery options and what must be verified | Guidance only; the agent cannot modify a reservation or confirm a seat |
| Refund guidance | Understand that refund eligibility depends on fare rules, ticket conditions, and disruption circumstances | Does not access ticket coupons, fare rules, payment systems, or refund status |
| Baggage support | Get allowance guidance and understand what to prepare for a baggage case | Does not trace, create, or update a baggage claim |
| Check-in guidance | Receive general check-in timing and process information | Does not check a passenger in or access airport systems |
| Special assistance guidance | Understand available request categories and when to contact Gulf Air | Does not submit or confirm an assistance request |
| FalconFlyer guidance | Receive general program and tier-aware guidance when context is available | Does not access a live loyalty account or confirm individual benefit eligibility |
| Passenger context | Use the selected passenger's booking, route, tier, and status when supplied | Context is request-scoped; sample records are demonstration data |
| Bilingual interaction | Respond in English or Arabic based on input or the selected language | Language selection is driven by request context/input; quality depends on the configured model |
| Sensitive-case handling | Recommend human review for medical, bereavement, legal, complaint, harassment, threat, safety, or emergency cases | Can create a local demo support case with a reference and simulated queue; does not contact or transfer to a human agent |
| New-flight search and booking | Search sample schedules, confirm a simulated booking, and download an itinerary confirmation | Stores a demo booking and reference; does not reserve live inventory, issue tickets, or process payment |

The agent is not a tourism, hotel-booking, or general itinerary-planning assistant in this Gulf Air support experience. Requests for general destinations, hotels, sightseeing, or travel plans should be redirected to the appropriate product experience.

## 3. System architecture and request flow

The customer-support chat is served by the LangChain.js API:

```text
Angular UI or API client
        |
        | POST /api/chat
        v
Express API (packages/api-langchain-js)
        |
        +-- Request-scoped passenger context and recent conversation history
        +-- Local policy, passenger, disruption, and rebooking data
        |
        v
Configured chat model
        |
        v
JSON-framed streamed response
```

The API also has MCP server configuration and agent construction code. In the current `TravelAgentsWorkflow.run()` request path, chat responses are produced through a direct model invocation with the prompt and local data; the constructed specialist/deep-agent runnables are not invoked to answer the message. As a result, a configured MCP server should **not** be interpreted as evidence that a customer request was served by a live Gulf Air system.

### Main implementation locations

| Concern | Location |
|---|---|
| Express API, health/tools/dashboard/chat routes | `packages/api-langchain-js/src/server.ts` |
| Demo flight search, booking, and support-case persistence | `packages/api-langchain-js/src/demo-workflows.ts` |
| Customer-support system prompt, context handling, and response generation | `packages/api-langchain-js/src/graph/index.ts` |
| Specialist/deep-agent construction | `packages/api-langchain-js/src/agents/index.ts` |
| MCP server URL configuration | `packages/api-langchain-js/src/tools/index.ts` |
| Local policy and demonstration data | `packages/api-langchain-js/data/` |

## 4. Runtime behavior

### 4.1 Request processing

For a non-greeting message, the workflow:

1. Determines the response language from `customerContext.preferredLanguage`, Arabic text, or an explicit Arabic-language request.
2. Handles simple greetings and thanks without requiring booking details.
3. Reads policy files and sample passenger, disruption, and rebooking data from the API's local `data/` directory.
4. Uses up to the last eight valid conversation turns supplied in `conversationHistory`.
5. Applies the selected passenger context to personal questions. If an explicitly supplied booking reference conflicts with the selected profile, the request is declined to protect passenger privacy.
6. Directs sensitive matters to official Gulf Air support rather than claiming to transfer the customer.
7. Directs new-flight purchase requests to the demo booking experience and clarifies that schedules/prices are demonstration-only.
8. Invokes the configured model and streams the resulting response.

The service does not retain a shared passenger context between API requests. The caller is responsible for resending the current context and relevant conversation history.

The Express process caches the workflow after its first `/api/chat` request. MCP tool selection/configuration used during that initialization is therefore process-scoped; changing the `tools` array on a later request does not rebuild the cached workflow.

Separately, the demo workflow API searches sample schedules, saves confirmed demo bookings, creates categorized support cases in simulated queues, and retrieves those records by demo profile ID. The UI can download plain-text itinerary confirmations and case summaries. Creating a case requires explicit customer confirmation; it does not contact a real support team.

### 4.2 Policy and safety rules in the prompt

The runtime prompt instructs the model to:

- Ground answers in the supplied policy, disruption, and passenger data.
- Avoid inventing fare rules, compensation, eligibility, or outcomes.
- Ask only the minimum necessary follow-up questions.
- Recommend human review for sensitive cases and avoid promises.
- Respond concisely and professionally, in the detected/requested language.
- Include a short source note for policy-based answers and identify when a policy cannot be verified.
- Treat sample records as demo-only and not claim live system access.
- Use only the selected passenger context for personal questions and avoid disclosing another passenger's data.
- Put the direct answer first, followed by a concise explanation and next step.

These are model instructions and application-level checks, not a substitute for service-side authorization or production identity verification.

## 5. Data sources and trust boundaries

The workflow expects these files under `packages/api-langchain-js/data/`:

| File | Use | Trust boundary |
|---|---|---|
| `gulf-air-policies.txt` | General disruption and customer-care rules | Demonstration policy content; verify against approved operational policy before production use |
| `baggage-policy.txt` | Sample baggage allowance guidance | Local static content; not route/fare-specific live allowance lookup |
| `refund-policy.txt` | Sample refund guidance | Does not represent an individual ticket's fare conditions |
| `checkin-policy.txt` | Sample check-in timing guidance | Does not account for all airport, route, or operational exceptions |
| `special-assistance-policy.txt` | Sample assistance request guidance | Does not create or confirm a service request |
| `falcon-flyer-policy.txt` | General loyalty program guidance | Does not access member account or confirm personalized eligibility |
| `flight-disruptions.json` | Sample flight statuses and disruption reasons | Static demonstration data; not a live operational feed |
| `passengers.json` | Sample passenger records | Demonstration data; not a production passenger database |
| `rebookings.json` | Sample rebooking records | Demonstration data; not a reservation-system transaction |
| `rebooking_options.json` | Optional sample recovery options | Missing file is treated as an empty option list by the workflow |
| `demo-workflows.json` | Server-backed demo bookings and support cases | Local JSON store for a single-instance demonstration; do not store sensitive data |

Do not submit passport numbers, payment-card details, authentication secrets, or other unnecessary sensitive data in prompts. Production use requires approved data sources, authentication/authorization, privacy controls, retention policy, and airline-approved policy content.

## 6. API contract

The base URL and port are deployment-specific. The examples below assume `http://localhost:4000`.

### 6.1 Health check

`GET /api/health`

Successful response:

```json
{
  "status": "OK",
  "orchestrator": "langchain-js"
}
```

### 6.2 Available MCP tools

`GET /api/tools`

Returns configured tool servers, their reachability, and discovered tools. A server may be omitted if its corresponding `MCP_*_URL` setting is not configured. The endpoint reports MCP availability; it does not establish that the customer-support message will use those tools.

### 6.3 Chat

`POST /api/chat`

Request content type: `application/json`

| Field | Type | Required | Description |
|---|---|---:|---|
| `message` | string | Yes | Current user message |
| `tools` | MCP server definition array | No at route validation; normally supplied by the UI | Tool-server definitions used when the process initializes its workflow |
| `customerContext` | object | No | Selected passenger context for this request |
| `conversationHistory` | array | No | Recent `{ "role": "user" \| "assistant", "content": string }` turns |

Supported `customerContext` properties:

| Property | Type |
|---|---|
| `bookingReference` | string |
| `passengerName` | string |
| `flightNumber` | string |
| `origin` | string |
| `destination` | string |
| `falconFlyerTier` | string |
| `bookingStatus` | string |
| `preferredLanguage` | `"en"` or `"ar"` |

Example:

```json
{
  "message": "My flight GF123 is delayed. What should I do?",
  "tools": [],
  "customerContext": {
    "bookingReference": "GA12345",
    "passengerName": "Demo Passenger",
    "flightNumber": "GF123",
    "origin": "BAH",
    "destination": "LHR",
    "preferredLanguage": "en"
  },
  "conversationHistory": []
}
```

Responses are streamed with `Content-Type: text/event-stream`. The current implementation emits JSON objects separated by a blank line. A typical metadata frame has this shape:

```json
{
  "type": "metadata",
  "kind": "langchain-js",
  "agent": "TravelAgent",
  "event": "agent_complete",
  "data": {
    "agent": "TravelAgent",
    "messages": [
      { "content": "Response text..." }
    ]
  }
}
```

The workflow can emit `workflow_error` events when model/data processing fails. Clients should handle incomplete streams and error frames rather than assuming every response ends successfully.

Example request:

```bash
curl -N http://localhost:4000/api/chat \
  -H "Content-Type: application/json" \
  -d "{\"message\":\"What is the general check-in policy?\",\"tools\":[],\"customerContext\":{\"preferredLanguage\":\"en\"},\"conversationHistory\":[]}"
```

### 6.4 Dashboard

`GET /api/dashboard`

Returns demonstration dashboard metrics, capability descriptions, follow-up prompt suggestions, and an assessment generated from the sample data. Dashboard values should not be treated as measured production KPIs unless replaced with validated telemetry and business data.

### 6.5 End-to-end demo workflows

| Method | Endpoint | Result |
|---|---|---|
| `POST` | `/api/demo/flights/search` | Returns three sample options for a supported route, date, passenger count, and cabin |
| `POST` | `/api/demo/bookings` | Saves a selected option and returns a `GD` demo booking reference |
| `GET` | `/api/demo/bookings?passengerId=<profile-id>` | Returns saved demo bookings for that profile |
| `POST` | `/api/demo/cases` | Saves a confirmed case summary and assigns a simulated support queue |
| `GET` | `/api/demo/cases?passengerId=<profile-id>` | Returns saved demo cases for that profile |

The store path is controlled by `DEMO_WORKFLOWS_FILE`, defaulting to `data/demo-workflows.json` relative to the API working directory. The containing directory must be writable. This file-based store is for a single process only; local filesystem state may not be shared between instances or retained by the hosting environment. Dashboard workflow counts come from these demo records; historical service KPIs such as CSAT, deflection, and first-contact resolution are not measured. Downloads are plain-text records from the demo response. No ticket, payment, live reservation change, refund, or real agent handoff occurs.

## 7. Prompt library

These are **user prompt templates** for interacting with the current support workflow. They are not new system prompts or a guarantee of a live transaction. Use demonstration identifiers only in local demo environments.

### 7.1 Flight delay

**Initial prompt**

> My Gulf Air flight `{flight_number}` from `{origin}` to `{destination}` is delayed. What general support options may apply, and what information should I confirm?

**Follow-up prompts**

- > The delay is about `{duration}`. Explain which guidance is supported by the policy data and what still needs airline verification.
- > My demo booking reference is `{booking_reference}`. Summarize only the matching selected passenger context and relevant next steps.
- > Draft a short message asking Gulf Air to confirm my recovery options.
- > Please provide the answer in Arabic.

### 7.2 Cancellation and refund

**Initial prompt**

> My flight was cancelled. Explain the general rebooking and refund options, and tell me what details affect eligibility.

**Follow-up prompts**

- > I have not travelled. What should I ask the airline to verify about my fare and ticket conditions?
- > Draft a neutral refund-review request. Do not state that I am eligible.
- > Keep the explanation to three concise bullet points.

### 7.3 Baggage

**Initial prompt**

> What baggage allowance guidance is available for `{cabin_class}`? Please identify any details that need to be checked against my ticket.

**Follow-up prompts**

- > My bag is delayed. Give me a checklist of information to provide when contacting baggage support.
- > My route is `{origin}` to `{destination}`. Can this local policy determine my exact ticket allowance?
- > Write a brief customer-service message asking how to submit a baggage claim.

### 7.4 Check-in

**Initial prompt**

> What are the general check-in timing guidelines for my upcoming Gulf Air flight?

**Follow-up prompts**

- > My flight departs from `{airport}` at `{time}`. Which details should I verify with the airport or airline?
- > I missed online check-in. Explain what the local guidance can and cannot confirm.
- > Make the answer concise and provide one next step.

### 7.5 Special assistance

**Initial prompt**

> I need `{assistance_type}` for an upcoming trip. What general guidance is available, and how do I request confirmation from Gulf Air?

**Follow-up prompts**

- > My flight is on `{date}`. What should I include in a support request?
- > Please create a short handoff summary without unnecessary personal information.
- > If this is urgent or medical, tell me clearly that an official human support team must review it.

### 7.6 FalconFlyer

**Initial prompt**

> I have a question about FalconFlyer `{tier_or_benefit}`. Explain the general program guidance and distinguish it from benefits that require account verification.

**Follow-up prompts**

- > Can you confirm whether I personally qualify for lounge access or extra baggage? If not, explain what needs to be checked.
- > Draft a message asking Gulf Air to verify my current tier benefits.
- > Respond in Arabic.

### 7.7 Sensitive case handoff

**Initial prompt**

> I need help with a sensitive `{case_type}` issue related to my trip. Please help me prepare a concise handoff for an official Gulf Air support professional.

**Follow-up prompts**

- > Ask only for the minimum details needed to summarize the case.
- > Draft the handoff in a neutral, empathetic tone without promising a result.
- > Do not include payment, passport, or unrelated personal details.

### 7.8 Verify system capability

**Initial prompt**

> For my question, separate what you can answer from supplied demo policy/data from anything that requires live Gulf Air system access.

**Follow-up prompts**

- > Can you check live booking, flight status, refund, check-in, baggage, or loyalty account information?
- > If you cannot complete the action, tell me what official channel or human team to contact.
- > List the minimum details I should have ready, excluding passport and payment information.

## 8. Operational and production considerations

Before a production deployment, the service owner should validate and implement at least the following:

- Replace local sample files with approved, versioned policy and operational data sources.
- Integrate live flight, reservation, ticket/fare, baggage, check-in, assistance, and loyalty systems only through authenticated and authorized service interfaces.
- Enforce user identity, passenger-to-booking authorization, least privilege, rate limits, and audit logging server-side.
- Define privacy, data minimization, redaction, retention, and regional data-handling requirements.
- Add explicit timeouts, retries, and surfaced errors for dependent systems.
- Establish human handoff integration and escalation service-level objectives.
- Replace the single-instance JSON demo store with a shared database and authenticated passenger authorization before retaining real booking or case data.
- Validate Arabic/English responses and policy citations with Gulf Air subject-matter experts.
- Add automated tests for policy grounding, passenger isolation, prompt injection resistance, and safe failure when a data source is missing.
- Instrument tool and model calls while ensuring logs do not expose unnecessary passenger data.
- Treat dashboard metrics as non-production until they are derived from validated telemetry and business systems.
